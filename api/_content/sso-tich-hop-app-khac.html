Tích hợp SSO cho app khác

Dành cho chủ app khác (chat, meeting, app mới sau này) muốn dùng chung đăng nhập với hệ thống hiện có thay vì tự làm auth riêng. Viết theo từng bước, kèm code mẫu thật lấy từ các service đang chạy.

1

Tổng quan hệ thống SSO

Điều kiện tiên quyết để tích hợp: app của bạn phải chạy trên 1 subdomain của cùng domain cha với các app đã có (vd chat.xaydung.vn nếu domain cha là xaydung.vn) — cookie đăng nhập chỉ dùng chung được trong phạm vi 1 domain cha.

App của bạn chỉ nói chuyện với gateway — không bao giờ tự lưu mật khẩu hay tự làm màn hình đăng nhập.

Thành phầnVai tròBạn cần biết gì
api-ssoPhát hành/xác thực token, giữ private key, quản lý danh sách app + ai được dùng app nàoAPI thuần, gọi qua gateway — không gọi thẳng
sso-webTrang đăng nhập/quên mật khẩu/trang chủ liệt kê app/quản lý tài khoản dùng chungRedirect người dùng sang đây khi chưa đăng nhập
api-gatewayCổng vào duy nhất, verify JWT qua JWKSMọi request (kể cả tới api-sso) đều qua đây

Các endpoint api-sso phơi qua gateway

MethodPath qua gatewayDùng khi nào
POST/api/loginĐăng nhập — body {username, password, remember}, username nhận cả tài khoản/email/số điện thoại
POST/api/refreshLàm mới access token khi hết hạn (đọc refresh cookie tự động)
POST/api/logoutThu hồi phiên + xoá cookie
GET/api/me?app=<app_key>Kiểm tra đã đăng nhập chưa + lấy thông tin user hiện tại. Kèm ?app= để tự chặn 403 nếu chưa được cấp quyền dùng app này — xem mục 3
GET/api/appsDanh sách app tài khoản hiện tại được cấp quyền (phục vụ trang chủ SSO)
POST/api/forgot-passwordBody {email} — gửi email chứa link đặt lại mật khẩu
POST/api/reset-password-confirmBody {token, newPassword} — token lấy từ link email

Token là JWT ký RS256, payload access token: {user_id, session_id, type:'access'} — không có sẵn tên/cây quyền (functions/actions), muốn có phải tự gọi GET /me.

Đăng ký trước khi code: mỗi app tích hợp cần 1 app_key (chuỗi định danh ngắn) do đội vận hành SSO cấp cùng lúc với domain con và cấu hình CORS — xin cả 3 thứ này trong 1 lần trao đổi, tránh vướng ở bước cuối lúc demo.

app_key đã đặt sẵn

4 app_key sau đã có trong danh mục app của SSO — nếu bạn đang làm đúng 1 trong các app này thì dùng lại, không xin key mới:

app_keyApp
financeTài chính (quản trị hệ thống + tài chính)
taskNhiệm vụ
chatTrò chuyện nội bộ
meetingCuộc họp

App mới ngoài 4 cái trên (không phải chat/meeting) mới cần xin app_key mới ở đội SSO.

Tích hợp web app

Đúng luồng các app hiện có đang chạy thật — copy được gần như nguyên văn.

sequenceDiagram
  actor U as Người dùng
  participant App as App của bạn
  participant GW as api-gateway
  participant SSO as api-sso

  U->>App: Mở app
  App->>GW: GET /api/me?app=<app_key>
  GW->>SSO: forward
  SSO-->>GW: 401 — chưa có phiên hợp lệ
  GW-->>App: 401

  SSO->>SSO: Xác thực, tạo phiên mới
  SSO-->>U: Set cookie access_token + refresh_token
(Domain=.xaydung.vn) rồi chuyển hướng về redirect
  U->>App: Quay lại app (trình duyệt đã có cookie)
  App->>GW: GET /api/me?app=<app_key>
  GW->>SSO: forward (kèm cookie)
  SSO-->>GW: 200 — {user, functions, is_admin}
  GW-->>App: 200

App không tự giữ trạng thái "đã đăng nhập chưa" — luôn hỏi lại qua /me lúc khởi động.

  1. Xin domain con + đăng ký CORS ở gateway Domain app phải là subdomain của domain cha dùng chung (để cookie Domain=.xaydung.vn đọc được). Báo cho người quản trị api-gateway thêm 1 pipeline + biến CORS riêng cho origin của bạn — không dùng chung biến CORS của app khác, vì package cors hiểu chuỗi origin là 1 origin literal, không tự tách theo dấu phẩy để so khớp động (lỗi thật đã gặp lúc làm sso-web — mỗi pipeline cần 1 biến origin riêng).
  2. Mọi request gọi API phải gửi kèm cookie 
    // axios
const apiClient = axios.create({ baseURL: GATEWAY_URL, withCredentials: true });

// fetch
fetch(url, { credentials: 'include' })
    Thiếu withCredentials / credentials: 'include' thì trình duyệt không gửi cookie httpOnly kèm request — lỗi phổ biến nhất khi mới tích hợp, biểu hiện là /me luôn trả 401 dù vừa đăng nhập xong.
  3. Chưa đăng nhập → redirect cross-origin sang sso-web 
    // Không dùng <Navigate>/router nội bộ - đích nằm khác origin
const SSO_URL = import.meta.env.VITE_SSO_URL; // vd https://sso.xaydung.vn
function redirectToLogin() {
  const redirect = encodeURIComponent(window.location.pathname + window.location.search);
  window.location.href = `${SSO_URL}/login?redirect=${redirect}`;
}
    redirect phải là 1 URL/path bạn kiểm soát được — sso-web tự chặn open-redirect (chỉ chấp nhận path nội bộ hoặc domain nằm trong whitelist cấu hình lúc build sso-web, cần báo trước domain của bạn để được thêm vào whitelist đó).
  4. Bootstrap phiên đăng nhập lúc app khởi động Gọi GET /me?app=<app_key> qua gateway 1 lần lúc app mount (không phải trong từng component con) — 200 thì lưu user vào state, 401 thì sang bước 3. Phải phân biệt rõ 3 trạng thái loading/authenticated/unauthenticated trong state — nếu chỉ có 2 trạng thái, lúc F5 trang sẽ có 1 khoảnh khắc bị hiểu nhầm là "chưa đăng nhập" và redirect oan trước khi /me kịp trả lời. Xem mục 3 để biết cách xử lý riêng khi gặp 403 thay vì 401.
  5. Access token hết hạn giữa chừng → tự refresh 1 lần 
    let refreshPromise = null;
apiClient.interceptors.response.use(null, async (error) => {
  if (error.response?.status === 401 && !error.config._retried) {
    error.config._retried = true;
    refreshPromise ??= apiClient.post('/refresh').finally(() => { refreshPromise = null; });
    await refreshPromise;
    return apiClient(error.config);
  }
  return Promise.reject(error);
});
    Dùng chung 1 promise đang chạy (không tạo request /refresh mới cho từng request 401 đến cùng lúc) — nhiều request song song lúc token vừa hết hạn mà mỗi cái tự gọi refresh riêng dễ sinh race, đây là bug thật đã xảy ra trước khi có SSO.
  6. Đăng xuất POST /logout qua gateway rồi xoá state phía client — service tự thu hồi session + clear cả 2 cookie (access/refresh) theo đúng domain đã set, không cần bạn tự xoá cookie tay (không xoá được vì httpOnly). Nhân tiện xoá luôn mọi bộ lọc/lựa chọn đã lưu ở localStorage riêng của app bạn — một phiên đăng nhập mới (có thể là người khác) không nên kế thừa lựa chọn của phiên trước.
Không tự làm form đăng nhập riêng. Mọi app dùng chung đúng 1 trang login (sso-web) — nếu app bạn cần giao diện khác biệt (branding riêng), trao đổi trước với đội SSO thay vì tự dựng form gọi thẳng /api/login, để tránh mỗi app một kiểu xử lý lỗi/2FA sau này.
3

Phân quyền theo app Mới

Đăng nhập được vào hệ thống và được dùng app của bạn là hai việc khác nhau — đừng nhầm lẫn.

Một token hợp lệ chỉ chứng minh "người này đã đăng nhập", không nói gì về việc họ có được cấp quyền dùng app của bạn hay không. Chỉ ẩn/hiện nút trên giao diện là không đủ: ai có cookie hợp lệ vẫn gõ thẳng URL vào được nếu tầng phía sau không tự kiểm tra.

Cách chặn đúng: luôn kèm app_key khi gọi /me

Kết quảÝ nghĩaApp nên làm gì
200Có quyềnRender giao diện chính
401Chưa đăng nhập / hết phiênChuyển hướng sang trang đăng nhập
403Đã đăng nhập, không có quyền dùng app nàyHiện trang "Không có quyền truy cập" + nút đăng xuất — không chuyển hướng sang trang đăng nhập
Lỗi thường gặp: gộp chung xử lý 401 và 403 thành "coi như hết phiên, đá về trang đăng nhập". Với 403, người dùng đăng nhập lại vẫn bị từ chối y hệt — tạo vòng lặp vô nghĩa và một thông báo lỗi sai bản chất (họ không hề "hết phiên", chỉ là chưa được cấp quyền).

Tài khoản có vai trò quản trị hệ thống luôn được đi qua bất kể app_key nào. Sai app_key (gõ nhầm lúc tích hợp) bị coi là "không có quyền" (an toàn hơn là "bỏ qua kiểm tra") — đừng để lỗi đánh máy vô tình tắt luôn lớp bảo vệ này.

Trước khi bật kiểm tra này cho app thật: đảm bảo mọi người dùng cần dùng app của bạn đã được cấp quyền trong danh mục app (đội SSO seed sẵn hoặc bạn tự vào trang quản trị cấp) — bật kiểm tra mà chưa cấp quyền sẽ khoá nhầm toàn bộ người dùng ngay lúc lên production.
4

Đồng bộ người dùng Mới

Nguyên tắc chung — cách làm chi tiết (tên API, tên bảng) do đội của bạn tự thiết kế, mỗi app một khác tuỳ nhu cầu.

Hầu hết app tích hợp đều cần một bản sao cục bộ của dữ liệu người dùng (tên, phòng ban, chức vụ...) để phục vụ nghiệp vụ riêng — vì CSDL người dùng "gốc" và CSDL của app bạn thường tách biệt, không join thẳng được. Phần này mô tả nguyên tắc, không phải một cách làm cụ thể.

sequenceDiagram
  actor Admin as Quản trị viên
  participant Core as App quản lý người dùng gốc
  participant Yours as App của bạn

  Admin->>Core: Tạo / sửa / xoá người dùng
  Core->>Core: Ghi vào CSDL của Core
  Core-->>Yours: Gọi API nội bộ để đồng bộ
(kèm khoá bí mật dùng chung giữa 2 bên)
  Yours->>Yours: Cập nhật (thêm/sửa/xoá mềm)
vào bảng người dùng cục bộ
  Yours-->>Core: Xác nhận đã nhận
(lỗi ở bước này chỉ ghi log, KHÔNG chặn thao tác chính của Core)

Mẫu tổng quát — tên API, tên bảng, khoá bí mật cụ thể do 2 đội tự thống nhất khi tích hợp.

Đầu vào API sync — ví dụ

App "nguồn sự thật" gọi sang app của bạn mỗi khi tạo/sửa/xoá người dùng. Payload cụ thể do 2 đội tự thống nhất — dưới đây là ví dụ các field thường gặp, để bạn hình dung lúc thiết kế bảng người dùng cục bộ:

// POST https://app-cua-ban.xaydung.vn/internal/sync/users
// Header: X-Internal-Secret: <khoá bí mật dùng chung>
{
  "user_id": "3f1e2a...-uuid",     // khoá chính, dùng để join với dữ liệu của bạn
  "user_name": "nguyenvana",
  "full_name": "Nguyễn Văn A",
  "email": "a.nguyen@xaydung.vn",
  "phone_number": "0901234567",
  "avatar": "uploads/2026-09-01/abc.png",
  "branch_id": 3,
  "branch_name": "Chi nhánh Hà Nội",
  "department_id": 8,
  "department_name": "Phòng Kỹ thuật",
  "position_id": 5,
  "position_name": "Trưởng phòng",
  "active_flag": 1                // 0 = đã xoá/ngừng hoạt động (xoá mềm)
}

// POST .../internal/sync/users/delete
{
  "json_list": [{ "user_id": "3f1e2a...-uuid" }],
  "updated_by_id": "system"
}

Bạn không bắt buộc nhận đủ toàn bộ field trên — chỉ khai báo trong hợp đồng API những field app của bạn thật sự dùng tới (xem nguyên tắc "chỉ đồng bộ trường bạn thật sự cần" bên dưới).

5 nguyên tắc khi thiết kế phần nhận đồng bộ

  • Idempotent (gọi lại nhiều lần vẫn ra cùng kết quả) — dùng "cập nhật hoặc tạo mới nếu chưa có" (upsert) thay vì "chỉ tạo mới", vì phía gọi có thể gọi lại nếu lần trước lỗi mạng.
  • Không chặn thao tác chính của Core — nếu app bạn tạm thời không phản hồi, việc tạo/sửa người dùng ở phía Core vẫn phải thành công, chỉ ghi log lỗi đồng bộ để xử lý sau.
  • Xác thực bằng khoá riêng cho việc này, không dùng JWT người dùng — đây là lời gọi giữa 2 hệ thống, không có người dùng cuối đứng sau. Dùng 1 khoá bí mật dùng chung (biến môi trường, giống nhau ở cả 2 phía), gửi qua header riêng.
  • Chỉ đồng bộ trường bạn thật sự cần — đừng sao chép nguyên cả bảng "cho chắc", đặc biệt tránh nhân bản thêm 1 nơi lưu các trường nhạy cảm không cần thiết cho nghiệp vụ của bạn.
  • Xoá mềm, không xoá cứng — khi Core xoá 1 người dùng, bản sao ở app bạn nên đánh dấu ngừng hoạt động thay vì xoá hẳn dòng dữ liệu, vì dữ liệu lịch sử (log thao tác, việc đã giao...) vẫn cần tham chiếu.
Không cần mục này nếu: app của bạn không cần hiển thị thông tin người dùng phong phú, chỉ cần biết "đây là user_id nào" — lấy thẳng từ token đã đủ làm khoá tham chiếu trong CSDL riêng của bạn, không cần đồng bộ gì thêm.
5

Giao diện dùng chung Mới

Hai điểm chạm nên có để trải nghiệm liền mạch giữa các app trong hệ thống.

Icon chuyển đổi app

Đặt 1 icon dạng lưới ở khu vực header (cạnh chuông thông báo/nút đổi theme), bấm vào chuyển hướng sang trang chủ sso-web — nơi liệt kê mọi app người dùng hiện tại được cấp quyền. Không cần gọi API gì thêm — chỉ là 1 liên kết tĩnh trỏ sang domain sso-web.

Liên kết "Quản lý tài khoản"

App của bạn không nên tự làm lại màn hình đổi mật khẩu/sửa hồ sơ cá nhân — dễ dẫn tới 2 nơi cùng ghi 1 dữ liệu theo 2 đường khác nhau, lệch dữ liệu về sau. Trang hồ sơ cá nhân trong app của bạn nên ở dạng chỉ xem, kèm 1 nút đưa người dùng sang trang "Quản lý tài khoản" của sso-web để họ tự sửa thông tin, đổi mật khẩu, hoặc xem/thu hồi các phiên đăng nhập đang hoạt động.

Đồng bộ chế độ sáng/tối (nếu app của bạn có dark mode)

Người dùng chuyển qua lại nhiều app trong ngày — nếu mỗi app tự nhớ theme riêng, họ sẽ thấy chớp sáng/tối mỗi lần đổi app dù vừa chọn dark mode ở app trước đó. Có sẵn 1 cookie dùng chung cho việc này, không cần hỏi đội SSO thêm gì — tự đọc/ghi theo đúng tên và định dạng dưới đây là dùng chung được ngay.

Thuộc tínhGiá trị
Tên cookiexdhy_theme_mode
Giá trị hợp lệ"light" hoặc "dark"
DomainDomain=.xaydung.vn (domain cha) — đọc/ghi được từ mọi subdomain, kể cả trang đăng nhập ở origin khác
Loại cookieCookie thường, không httpOnly (JS tự đọc/ghi được) — không dùng cookie này cho bất cứ thứ gì liên quan xác thực
 
// Đọc lúc khởi động - đặt data-theme lên <html> TRƯỚC khi app render
// (đặt trong effect sẽ bị nháy sai theme 1 nhịp lúc load trang).
function getInitialTheme() {
  const match = document.cookie.match(new RegExp('(?:^|;\\s*)xdhy_theme_mode=([^;]*)'));
  return match && decodeURIComponent(match[1]) === 'dark' ? 'dark' : 'light';
}
document.documentElement.setAttribute('data-theme', getInitialTheme());

// Ghi lại mỗi khi người dùng đổi theme trong app của bạn
function setSharedTheme(mode) { // mode: 'light' | 'dark'
  const domainPart = COOKIE_DOMAIN ? `; Domain=${COOKIE_DOMAIN}` : '';
  document.cookie = `xdhy_theme_mode=${mode}; Path=/; Max-Age=${400*24*60*60}; SameSite=Lax${domainPart}`;
  document.documentElement.setAttribute('data-theme', mode);
}
Không bắt buộc: nếu app của bạn chưa có dark mode, bỏ qua mục này — cookie không đọc được thì các app khác tự dùng theme mặc định (sáng) của họ, không có gì hỏng.
6

Tích hợp app mobile

Mobile không dùng lại được cơ chế cookie tự động của trình duyệt, nhưng không cần endpoint mới — dùng đúng các endpoint như web, app tự đọc token từ response rồi tự đính vào request sau. api-sso đã hỗ trợ sẵn: /me nhận Authorization: Bearer, còn /refresh//logout đọc token từ header Cookie (do cookie-parser parse) nên client tự dựng header đó được.

sequenceDiagram
  actor U as Người dùng
  participant App as App mobile
  participant GW as api-gateway
  participant SSO as api-sso
  participant KC as Keychain / Keystore

  U->>App: Nhập tài khoản/email/sđt + mật khẩu (form native của app)
  App->>GW: POST /api/login {username, password, remember:true}
  GW->>SSO: forward
  SSO-->>App: 200 {user} + header Set-Cookie: access_token=... ; refresh_token=...
  App->>App: Đọc 2 giá trị token từ header Set-Cookie
  App->>KC: Lưu access_token + refresh_token
  Note over App,GW: Request nghiệp vụ về sau
  App->>GW: GET /api/... , header Authorization: Bearer <access_token>
  GW-->>App: 200 (hoặc 401 nếu access token hết hạn)
  App->>GW: POST /api/refresh , header Cookie: refresh_token=<...>
  GW->>SSO: forward
  SSO-->>App: 200 + Set-Cookie: access_token=... (mới)
  App->>KC: Ghi đè access_token mới

Không WebView, không custom URL scheme. App tự đóng vai "cookie jar": đọc token ở Set-Cookie, cất an toàn, tự gửi lại.

Từng bước phía app

  1. Đăng nhập POST /api/login với JSON {username, password, remember: true} (remember:true để refresh token sống 30 ngày). Response 200: body là thông tin user; 2 token nằm ở header Set-Cookie (2 dòng access_token=..., refresh_token=...). Đọc giá trị token, bỏ qua các thuộc tính Path/HttpOnly/Max-Age.
  2. Cất token Lưu 2 token vào Keychain (iOS) / Android Keystore (qua EncryptedSharedPreferences) — không để ở UserDefaults/SharedPreferences thường.
  3. Gọi API nghiệp vụ Gắn header Authorization: Bearer <access_token> cho mọi request qua gateway. Gateway và middleware xác thực của các service đã đọc theo thứ tự "cookie trước, header Authorization sau" nên không cần đổi gì phía service.
  4. Access token hết hạn (401) POST /api/refresh với header Cookie: refresh_token=<refresh_token> (tự dựng chuỗi, không phải cookie thật của OS). Response 200 kèm Set-Cookie: access_token=... mới — ghi đè access token đang lưu rồi gọi lại request gốc. Nếu /refresh trả 401 → refresh token bị thu hồi/hết hạn → xoá token, quay về màn đăng nhập.
  5. Đăng xuất POST /api/logout với header Cookie: refresh_token=<...> để service thu hồi đúng session trong DB, rồi xoá cả 2 token khỏi Keychain/Keystore.
  6. Quên mật khẩu Gọi POST /api/forgot-password {email} — người dùng nhận email, bấm link mở sso-web trong trình duyệt hệ thống để đổi mật khẩu (app không cần xử lý màn đổi mật khẩu).
Lưu ý HTTPS: ở production cookie set kèm Secure — chỉ có nghĩa với trình duyệt; client mobile tự quản token thì bỏ qua, nhưng vẫn phải gọi gateway qua HTTPS để token không đi qua mạng ở dạng rõ. Access token mặc định sống 15 phút (hoặc 1 ngày nếu remember:true) — đừng hard-code, cứ bắt 401 rồi refresh.

Checklist trước khi go-live

  • Đã có app_key, domain con, cấu hình CORS được đội SSO xác nhận.
  • Bootstrap app gọi GET /me?app=<app_key>, không phải /me trơn.
  • Xử lý riêng 401 (chuyển hướng đăng nhập) và 403 (thông báo không có quyền, không chuyển hướng).
  • Đã cấp quyền dùng app cho toàn bộ người dùng cần dùng ngay — trước khi bật kiểm tra ?app=.
  • Trang hồ sơ cá nhân trong app chỉ hiển thị, có liên kết sang "Quản lý tài khoản" của sso-web.
  • Icon chuyển đổi app ở header trỏ đúng về trang chủ sso-web.
  • Nếu có đồng bộ người dùng: đã kiểm thử tạo/sửa/xoá ở nguồn, xác nhận đồng bộ đúng kể cả khi app của bạn tạm thời offline (nguồn vẫn phải thành công).
